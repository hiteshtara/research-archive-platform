# DEV pilot dry runs — the eight roles

> **Also run against the deployed artifact.** This file records the plan the
> utilities produce when compiled from source. The same eight roles have since
> been run through the image the DEV service actually runs, pinned by digest -
> see [`DEV_PILOT_DRY_RUNS_REV89.md`](DEV_PILOT_DRY_RUNS_REV89.md), which also
> covers PARENT_AWARD depth 0 and 1, the Kuali PERSON_ID requirement, and the
> expiry/revocation/cleanup procedures.

**Nothing here has been run against DEV.** Every block below is real output
from the real commands, produced by `PilotDryRunPlanIntegrationTest` against a
throwaway PostgreSQL with every committed migration applied. The plan is
output, not prose: a provisioning plan written by hand is a guess about what
the utilities will say, and these are the utilities saying it.

Each run omits `--confirm`, which is the utilities' default. The test asserts
afterwards that no link, no grant and no audit row exists, so this cannot
become a way to provision something by accident.

## The identifiers are placeholders, deliberately

The ARPs and Cognito subjects below are placeholders. Real pilot identities
come from BU IAM and the Cognito user pool and must be handed over out of
band, never committed — the verification procedure is
[`PHASE2_PILOT_PLAN.md`](../security/PHASE2_PILOT_PLAN.md) section 4b, and it
has not been shortcut here. What this proves is the SHAPE of each run: which
flags, which refusals, which notes.

The **scope values are real**, read from the live DEV API on 2026-11-10:

| Value | What it is | Verified |
|---|---|---|
| unit `1250000000` | parent unit with children `1250400000` and grandchild `1252060000` | acceptance matrix, 2026-10-29 |
| IO `9500234095` | `account_number` on Award `100004-00002` (award_id 2) | acceptance matrix, 2026-10-29 |
| Award `100380-00001` | a real hierarchy root with **eight** children, `-00002` to `-00009` | live Award search, 2026-11-10 |
| PERSON_ID `1000570` | a real `award_person.person_id` in an approved role | acceptance matrix |

`100380-00001` was chosen over the other candidates because eight children
make depth behaviour unambiguous: at depth 0 the grantee reaches one Award, at
depth 1 they reach nine. A parent with a single child cannot distinguish
"expansion worked" from "expansion did nothing".

A negative control from a different family — `100330-00002`, whose root is
`100330-00001` — must stay unreachable. The hierarchy walk compares
`root_award_number` on every hop precisely so a grant cannot cross families.

### Three things the output makes visible

**Every grant is proposed with an expiry.** D-ADM-3 made expiry optional with
no default, which is right for a production grant and wrong for a pilot: an
unreviewed pilot grant would otherwise become permanent through inattention.
`2027-06-30` is a proposal, not a decision.

**The expiry note is a real caveat, not boilerplate.** The utility reports:

> V087 constrains UNREVOKED grants, so after expiry this grant still occupies
> its scope until it is revoked.

So an expired pilot grant still blocks a replacement grant for the same scope.
Closing the pilot means **revoking**, not waiting.

**Roles 7 and 8 get no grant run at all.** The output says so explicitly
rather than silently skipping it. If a future run names either of them as a
grantee, the pilot has spent its controls.
